faq:
  - q: "Can space admins view the Jira audit log?"
    a: "Not unless they also hold the Administer Jira global permission, which Jira's built-in audit log requires. Configuration Monitor puts a change log in each space's settings sidebar instead, so any admin of a space can see what changed there, when, and who made the change, without a ticket to a site admin. People who cannot open the space settings do not see it."
  - q: "What configuration changes does Configuration Monitor track?"
    a: "Thirteen sections of each space's configuration: permissions, notifications, workflows, screens, work item security, roles, work types, components, versions, general settings such as name and lead, sprints on Scrum boards, and Jira Service Management queues and request types. Team-managed spaces skip components and versions, Kanban boards skip sprints, and field changes on team-managed work type screens cannot be tracked. It reads configuration, not the content of work items."
  - q: "How does Configuration Monitor know who changed a setting?"
    a: "It matches each detected change against Jira's own audit log records, by entity name and by section. When several admins changed the same setting in one period, all of them are listed. Some changes may stay unattributed: bulk operations, scheme edits that affect several spaces at once, and changes made through third-party integrations may not leave a matching audit record."
  - q: "Does the Atlassian Guard audit log show Jira configuration changes?"
    a: "It can, at organization level. With Atlassian Guard, organization admins get an audit log in Atlassian Administration that keeps activity for 365 days. Jira's app admin log, which tracks configuration and permission changes, appears there with Guard Standard plus Jira Premium, with Jira Enterprise, or with Guard Premium. It is built for organization, unit and site admins. Configuration Monitor answers the same question inside one space, for that space's admins."
  - q: "What personal data does it store, and how are GDPR requests handled?"
    a: "The only personal data it keeps is Atlassian account IDs and display names, recorded for change attribution and for manual syncs. Site admins handle requests in the GDPR Admin Panel: export a person's records as CSV for a right of access request, or anonymize them for erasure. Anonymizing replaces the display name with \"Anonymized User\" in every earlier record and keeps the account ID for audit purposes. Changes the person makes afterwards are attributed normally."
  - q: "How long does Configuration Monitor keep change history?"
    a: "One year. Change records older than a year are purged automatically, and each space keeps at most 1,000 change records. History starts at installation, because the first snapshot is the baseline, so changes made before you install it do not appear. A space's history can also be cleared from the app, and all stored data is deleted when the app is uninstalled."
  - q: "Where does Configuration Monitor store its data?"
    a: "In Forge storage on Atlassian's own infrastructure. The app is built on Atlassian Forge and is eligible for the Runs on Atlassian program, so its data stays on the Atlassian platform and Atlassian is its only sub-processor. Forge encrypts the data at rest and in transit. The app reads configuration such as schemes, workflows, roles and sprints, not the content of your work items."
  - q: "How do I install Configuration Monitor, and what does it cost?"
    a: "A Jira site admin installs it from the Atlassian Marketplace, where the current pricing and a free trial are listed. It is a Jira Cloud app with no Data Center version, and it works in company-managed and team-managed spaces in Jira and Jira Service Management. The first snapshot runs on install and hourly syncs start on their own, so changes appear within an hour."
